# Tokenizer Management — infrastructure developed specifically for Turkish

[Türkçe](README.md) · [System overview](../../architecture/SYSTEM_OVERVIEW.md) · [Architecture contract](../../architecture/CEVAHIR_ARCHITECTURE_SPEC.md)

**Updated: 20 September 2026.** Cevahir's tokenizer layer combines a BPE vocabulary and merge rules with text-processing components developed for Turkish. Tokenizer training, encoding/decoding and the preparation of model-training records share this infrastructure.

## Its contribution to the system

This module connects text to the numeric identities used by the model. Developers can inspect vocabulary, BPE merges, normalization and optional language-processing settings. Data preparation and inference use the infrastructure while preserving token meanings. Work on language representation can therefore be traced into the model's training inputs.

Turkish-specific work includes handling Turkish letters, optional `I → ı` / `İ → i` conversion, syllabification and rule-based morphology helpers. The model learns from token sequences during training; tokenizer processing alone does not teach it a language.

## One tokenizer, multiple languages

**Working in another language does not necessarily require a separate tokenizer specific to that language.** The same vocabulary and BPE merges can serve multiple languages whose text they can represent. The relevant questions are whether preprocessing preserves the characters, whether the vocabulary/subwords cover the text and how efficiently it is tokenized. The model's language capability also depends on training data and learned weights.

Cevahir's current preprocessor filters for ASCII letters, Turkish letters and digits; its standard cleanup also removes some symbols beyond `.,!?`. This version does not represent all Unicode text losslessly. That is a boundary of the current representation to develop, not a requirement for a separate tokenizer for every language.

`text_loss_policy` checks non-whitespace characters dropped by the pretokenizer after role-tag cleanup and normalization. `warn` is the default, `error` rejects such input and `ignore` disables the check. It does not establish losslessness across all normalization/decoding transformations or character ordering. The encoder's character fallback is also not byte fallback.

## Processing flow

```text
Raw text
  → TokenizerCore
  → BPEManager: role-tag cleanup and normalization
  → Pretokenizer: configured cleanup and segmentation
  → optional whole-word / syllable / morphology items
  → BPEEncoder: vocabulary, merge ordering and fallback
  → (text tokens, token IDs)
  → model input or training record

IDs generated by the model
  → BPEDecoder and final text processing
  → text
```

| Component | Role |
|---|---|
| [TokenizerCore](../../../tokenizer_management/core/tokenizer_core.py) | Shared API for train/inference settings, encode/decode, batches and training records |
| [BPEManager](../../../tokenizer_management/bpe/bpe_manager.py) | Coordinates vocabulary/merges, encoder/decoder/trainer and preprocessing |
| [BPETrainer](../../../tokenizer_management/bpe/bpe_trainer.py) | Develops merges and vocabulary from training sequences |
| [BPEEncoder](../../../tokenizer_management/bpe/bpe_encoder.py) | Converts text pieces into IDs using vocabulary and ordered merges |
| [BPEDecoder](../../../tokenizer_management/bpe/bpe_decoder.py) | Produces text from IDs and applies final processing |
| [Pretokenizer](../../../tokenizer_management/bpe/tokenization/pretokenizer.py) | NFC, configured case conversion, cleanup and segmentation |
| [Syllabifier](../../../tokenizer_management/bpe/tokenization/syllabifier.py) | Turkish syllabification rules |
| [Morphology](../../../tokenizer_management/bpe/tokenization/morphology.py) | Rule-based stem/suffix and form helpers |

## When do the language components run?

`include_whole_words`, `include_syllables` and `include_sep` affect the representation sequence. In the main tokenization path, morphology items are added only when both syllabification and the BPE setting `include_morphology` are enabled; the current call passes syllables into morphology. This path should not be described as a guarantee of complete word-level linguistic analysis.

TokenizerCore's standard inference profile disables syllabification. Training and inference defaults may differ; inspect explicit call arguments and effective configuration. Out-of-vocabulary fallback paths and explicit syllable/morphology expansion are separate operations.

The basic return contract is:

```python
def encode_model_input(tokenizer, text):
    tokens, token_ids = tokenizer.encode(text, mode="inference")
    # token_ids are the numeric model input; tokens are text pieces.
    return token_ids
```

## Connecting data and model use

[DataLoaderManager](../../../data_loader_management/data_loader_manager.py) reads text and question-answer sources. TokenizerCore builds ID sequences, targets and source information for training. [Cache preparation](../../../training_system/prepare_cache.py) stores these records for subsequent runs. [train_bpe.py](../../../tokenizer_management/train_bpe.py) is the entry point for creating a tokenizer; settings live in [config.py](../../../tokenizer_management/config.py).

When using a trained model, preserve its vocabulary, merges and effective BPE settings. [Cache identity](../../../training_system/cache_identity.py) and the [checkpoint contract](../../../model_management/checkpoint_contract.py) check this relationship. Two vocabularies of the same size may assign different meanings to the same IDs.

Working with a new language does not automatically mean changing the vocabulary or retraining the tokenizer. First evaluate the current representation. If it changes, consider tokenizer identity, prepared data and weight compatibility together; retain the historical training assets.

## Development scope

Unicode coverage, transformation losses, token efficiency and the effects of optional language components can be evaluated together. The aim is to expand representation coverage while retaining the work developed for Turkish. Priorities are recorded in the [development roadmap](../../architecture/NEXT_DEVELOPMENT_ROADMAP.md). This guide makes no unmeasured quality or speed superiority claim over other tokenizers.
